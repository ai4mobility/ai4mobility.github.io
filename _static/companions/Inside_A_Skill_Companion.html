Inside a skill: two transportation skills, opened up

You have seen what is inside a tool: a name, a description, an input schema, and code that runs. This page opens two skills the same way. One turns FDOT District 7's hurricane signal SOP into action cards. The other prepares a journal-club review from the instructor's guide. You will see how each skill is packed into a folder, how its SKILL.md sends the model to the right file at the right step, and how to turn your own transportation know-how into a skill. At the end, you will see what changes in the answer when the skill is installed and when it is not.

A skill is a binder for an agent

A skill is a folder of know-how for one job. In every chat, the model sees a short description of each skill. It opens a skill's folder only when a request matches, and it reads the other files in the folder only when a step needs them.

You already work this way. A new signal engineer joins District 7 in October. On her first storm morning, a supervisor hands her a binder. It has a cover note, the SOP pages, a sheet of crew slang, lessons from past storms, a calculator for refuel times, a blank action-card form, and a note on which calls belong to the TMC. She does not read it cover to cover. She opens the tab she needs. A skill is that binder, written for an AI agent.

Every part of the binder has a home in the skill folder, and each home is opened at a different moment. Only the cover note (the description) is in front of the model all the time. The calculator runs and hands back an answer; the model never has to read its code.

Skills and tools work together. A skill can tell the model which tools to call and what to check in their results. The D7 skill's rules.py and check_cards.py run through the agent's shell tool. A skill for SUMO work could tell the model when to call your SUMO tools, how many seeds to run, and what to check before reporting.

Three levels of loading

The description is small and always loaded. The body is read once the skill is chosen. The big files wait until a step asks for them. Scripts are different: the model runs them, and only what they print comes back. The bottom row shows what each real run on tab 4 actually read. Counts use the o200k tokenizer as an estimate; Claude's own tokenizer gives slightly different numbers.

The Agent Skills specification puts it in three lines: about 100 tokens of name and description for every skill at startup, a SKILL.md body under 5,000 tokens (and 500 lines) when the skill is activated, and other files "only when required". Both course skills fit comfortably: the D7 body is 1,653 tokens and the journal-club body is 1,254.

PartWhat goes in itRule of thumb
SKILL.mdFront matter (name, description, license, metadata), then the instructions: the file map, how knowledge is sorted, the steps, the output, sources, limits.Required. Keep the body short; point to files instead of pasting them in.
references/Text the model reads and quotes: the source's exact words, the glossary, the gaps, lessons, practice, checklists.One topic per file, one level deep from SKILL.md, so the model can open just the part it needs.

Why split the know-how into files at all? The model pays for every token it reads, and a long context buries the part that matters. The D7 folder holds 24,896 tokens of text and code outside its tests. One chat needs the 144-token description, plus only what the job calls for.

Read the SKILL.md: how it sends the model to the right file

A file path in SKILL.md does nothing by itself. A step has to name the file, say when to open it, say how much to read, and say what to do with what it finds. Start with the map, then read the real SKILL.md block by block.

Two things to notice

The model does not follow every line to the letter. Step 3 of the D7 skill says to read one phase, but the run read the whole SOP file and the scripts' source code. With a 6,246-token SOP, that costs little. With a 300-page manual, it would cost a lot. The fix belongs in the folder, not in the wording: put one phase in each file.
The checks passed the first time. In both runs the checker found nothing to fix, so the "fix every FAIL" loop never ran. The bad examples in evals/fixtures/ show what the checkers catch when they are needed: four planted card mistakes in the D7 skill, and seven failed checks on a bad set of journal-club notes.

Turn your transportation know-how into a skill

Write a skill for a job, not for a document. The same SOP could become three skills: one that looks things up, one that writes action cards, and one that checks a plan. Start from the job. Then sort what you know, because each kind of know-how breaks in its own way.

Sort before you write. A model miscounts hours, so rules go to code. It skips or reorders steps, so procedures become numbered steps. It loses a clause in a long text, so guidance is read one section at a time. It overreaches on decisions, so judgment goes to a named person. It turns a good story into a rule, so experience stays labeled as a suggestion. Gold homes are where a person stays in charge.

Get the experience: interview someone who has done the work

The part of a skill no model has read is in people's heads. Twenty minutes with an operator, an inspector or a crew lead fills practice.md and the glossary. These questions are condensed from the repository's docs/INTERVIEW_THE_EXPERT.md.

Ask aboutQuestions
WordsWhat do the crews call this? Which words in the manual does nobody use?
Order and timingWalk me through the first three hours. Which steps happen in a different order in practice?
Gaps and decisionsThe manual says a person decides. How do they decide, and what do they look at? What comes up every time that the manual doesn't cover?
Ask aboutQuestions
MistakesWhat do new staff get wrong in their first storm? Show me a card or report you would send back.
Exceptions and safetyWhen do you not follow the manual word for word? What should a computer never decide here?

What makes a skill worth having


A strong model already reads, writes and reasons well. A skill is worth what it gives the model that the model cannot get any other way. The with/without runs on tab 7 and a 2026 benchmark point to the same five things, in roughly this order.




The journal-club lesson. When reading the paper, all three journal-club runs found the same six planted problems: the 32% that is in no table, the contradicted gap, "eliminates" only at 100%, the missing field data, the single seed, and the stock phrases. The skill did not make the model a sharper critic. It made the answer fit the group: the guide's six parts in a format a script can check, ten slides for twenty minutes, the opinions handed back to the presenter, and no references cited from memory. Write skills for what the model can't know, not for what it already does well.


What a benchmark found




Short, focused skills written by people helped most. Long ones barely helped, and skills an agent wrote for itself made it worse. SkillsBench (arXiv 2602.12670 v4, June 2026) ran 87 tasks in 8 domains under 18 model-and-harness setups. Curated skills raised the average pass rate from 33.9% to 50.5%. Skills hurt on 13 of the 87 tasks; adaptive cruise control was among the largest drops (−5.6 points). The common cause was "a single “correct” pipeline without applicability boundaries or lightweight fallbacks".

The same request, with and without the skill


For each skill, one task from its evals.json was run three ways by the same model, each time in a fresh session. The model had no skill, then the source document attached, then the skill installed. Each answer was graded against the expectations that the skill's authors wrote before any run.






How fair is this comparison?


The baselineThe same model (Claude Opus 5.5) answered the same user message with the same attached file. Each run started in a fresh session with no web search and no other skills. Only what the model could see changed: nothing, the document, or the skill.


Why the grading is honestThe expectations come from evals.json, written on Nov 15, 2026, before any run. Every answer and every trace is shown here in full, so you can check each grade yourself.


The ugly casesThere was one run per condition. The repository's rule asks for three, so a one-point difference could be chance. The grader (the AI assistant that built this page) knew which answer was which. The scenario and the paper are synthetic. The checker rows test the skill's own format, which runs A and B never saw. Run A for the journal club also looked in the user's saved memory; it found only that a weekly journal club exists.










Fit card and check yourself


Fit card — Agent skill


Idea in one sentenceA folder of know-how for one job, made of instructions, reference text, code and formats, that an agent opens only when a request needs it.


Why it works (the logic)The model can already reason. What it lacks is your agency's exact words, numbers, decision rights and lessons. A skill gives the model those at the moment of need, in the order an expert uses them, and checks the result in code.


Fits these tasksRepeated jobs that follow a written procedure or guide plus experience: SOP-driven response, manual lookups, warrant and layout checks, review and report formats, data-reading recipes. Leverage: retrieval, generation, extraction, and support for judgment.


Needs this dataThe source document (edition, date, pages) and its reuse terms; field words; lessons and practice with dates and roles; a few test requests and tasks with expected answers. No training data and no fine-tuning.


Breaks whenThe description doesn't match how people ask; the source changes and nobody re-checks; the skill is long or rigid with no fallback; experience is passed off as a rule; nobody runs the checker.


Keep the classical method whenThe job is a fixed calculation or form (write a tool or a program). The question is one-off (attach the document). The decision belongs to a licensed engineer or the person the SOP names: the skill drafts, and that person decides. The trained human with the binder is still the baseline.

Check yourself


1. A classmate wants to paste all of MUTCD Part 6 into SKILL.md "so the agent knows everything." What do you tell them, and where should the material go?
Keep the SKILL.md body short (under 5,000 tokens) and make it a reading path. Put the provisions the job needs in references/, one topic per file, quoted with section and paragraph. Put taper lengths and sign spacing in scripts/ with tests. SkillsBench found that "comprehensive" skills added +0.7 points, against +19.0 for compact ones, and a long context buries the clause that matters.


2. Your SOP says crews "should consider" removing signal heads before landfall. An experienced crew lead tells you "we never do that." How does each piece enter the skill, and what should the agent's answer look like?
The SOP line is a procedure with the weight "consider", quoted word for word in references/. The crew lead's view goes in practice.md with their role and the date. The answer gives the SOP card with its weight (never raised to "must") and a separate Suggestion that cites the practice entry, says the two conflict, and names who decides. The skill does not pick a winner. The D7 skill handles the real version of this conflict (lesson L3) by giving both sides.


3. In the D7 comparison, the document-only run had the full SOP text and still lost points. Which part of the skill made the difference, and could pasting the document better have fixed it?
The points were lost on gaps, not reading. The document-only run told the TMC to rank signals with "the Priority #1 list from the zone maps". The SOP refers to both, but Appendix B is blank and no list exists. Only someone who knows the document can write that down; gaps.md did, and step 7 made the model read it. The same holds for "Who": the run made up roles because nothing told it that Appendix C is blank. No amount of better pasting adds knowledge that is not in the document.


4. Your project team trained its own model for post-storm damage classification. Would a skill replace it, help it, or not apply? What would the skill contain?
A skill would not replace a trained classifier; it can wrap one. It could say when to call your model as a tool, which damage codes the agency's form uses (in assets/), when to answer "unsure", which images need a person, and what to check before a report goes out (a checker in scripts/). Your comparison then has three arms: your model alone, a general model with no skill, and a general model with the skill and your model as a tool.
