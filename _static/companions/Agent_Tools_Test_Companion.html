The six questions, and the trap in each

How the test was kept fair
  • Each question and its checked answer were written, and checked in the data, before any run.
  • Work-zone questions use the saved Nov 5 2026 snapshot of FDOT's feed, so "right now" means . SUMO questions use the Fowler Ave scenario with seed 1. In A, B and C the simulation is advanced to the question's time before Claude's first turn; in R, Claude must run SUMO to that time itself.
  • Every run starts in a new, empty folder, with no project notes and no other tools. In A, B and C the only way to the data is the tools; in R the only way is code, with the data files copied in.
  • The tool server has the same name in A, B and C, so the name gives nothing away.

Scoreboard and cost

Are the tools themselves right?

An agent can only be as right as its tools. Two kinds of evidence say the tools themselves work: tests that check every claim the tools make, and a direct check of what each server hands the model in each setup.

What it shows, and what it does not

What the runs show, how far to trust them, when to build tools like these, and how to run the test on your own tools.

Fit card — Engineer-written tools for an agent

Idea in one sentence
Put the transportation knowledge (lane order, units, what "unknown" means, when a reading is valid) into the tool's code, description and result, so the model gets a correct, already-read answer instead of raw fields.
Why it works (the logic)
The model only reads text. A tool that returns "right lane of 3 closed" removes the step where a general model must interpret a field it has never seen defined, and the tool's tests make that interpretation checkable once, not re-guessed on every run.
Fits these tasks
Questions an agency asks again and again over the same data: work-zone checks, queue and lane readings, signal-plan checks. retrieval extraction judgment
Needs this data
A feed or simulator with a stable format · known cases with checked answers for the tests · someone who knows what each field means (the engineer).
Breaks when
The feed changes format; a question falls outside what the tool answers, so the model improvises with other tools; or the tool's own rule is wrong (tests only catch what someone thought to test).
Keep the classical method when
A one-off question that an engineer answers by looking at the data once, or a fixed question asked on a schedule, where a plain script (no model at all) gives the same answer every time.

Check yourself

1. Open busch_lanes in setup A (tab 2). The toolkit's get_work_zones misses the closure when the street is typed "Busch Blvd", but finds it for "East Busch Boulevard" or a search by distance. Did Claude find it? If the answer is wrong, is it the model's fault or the tool's, and what would you change, in which file?

Notes

No, in none of the three repeats. Each time Claude asked get_work_zones for "Busch Blvd" and got back one record, the one with no lane data, but not the eastbound record with the closed lane, so it reported the lane closures as unknown. Claude reported what it was given, so the miss is the tool's. The fix goes in the tool server's code and its tests: make the street search return every record for the street, say how many nearby records it could not match by name (as work_zones_on_street does: "Not findable by name: 5 active records within 5 mi"), and add a test that asks for "Busch Blvd" and expects the eastbound closure.

2. Setup R writes its own code over the raw files. Pick one trap from tab 1 and say how a careful programmer who is not a traffic engineer could still fall into it, and how a tool prevents it.

Notes

The lane trap is the clearest. WZDx counts lanes from the left and lists shoulders as lanes, so the closed lane is "lane 4 of 5" in the feed. Code that reads the field correctly still reports "lane 4 of 5", which an operator reads as the wrong lane; R did this in all three repeats. The tool converts it once, in tested code, to "the right lane of 3 travel lanes".

3. Your agency wants an agent that answers work-zone questions for TMC operators. Which three facts from this page would you show the TMC manager, and what would you still need to test before it goes live?

Notes

For example: setup C was right in every run on both tracks, against fewer for A and R (tab 4); the same setup gave the same grade on repeats in almost every case; and the tools pass their own tests (tab 5). Still to test: questions from real operator requests, written before the runs; the live feed instead of a snapshot; what happens when the feed changes format or goes stale; and where an operator confirms an answer before it is acted on.

Run it yourself

The kit is in the class folder, M5-8_AI_Agents_and_RL/agent_tools_demo/, with a README. It needs Claude Code logged in and Python with mcp (and SUMO for the SUMO questions). Then:

python demo.py check --with-claude   # Claude sees and calls the tools in every setup
python demo.py live busch_lanes C     # one run, the loop printed as it happens
python demo.py run --repeats 1        # all six questions in all four setups
python demo.py report                 # grading sheet, numbers, transcripts

Try your own tools the same way: put your contribution's server.py in a setup and ask your own questions with live --ask.
